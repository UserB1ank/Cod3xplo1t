# Cod3xplo1t 项目评估与重构建议

日期：2026-11-16。目标依据：主 Agent 自主协调，包含动态复现与验证。

## 判断

建议重构核心执行体系，保留已经有价值的输入、证据、权限和存储能力。现阶段不宜直接整仓重写，也不宜继续把原有所有开放 Issue 当作必须兑现的路线图。

SCG → ASG → AuditPath → Agent → 验证是一条合理的分析链，但完整产品还需要另一条主线：目标 → 调查与委派 → 假设 → 验证 → 证据 → 下一步调查。静态分析为这条主线提供事实；主 Agent 决定调查安排，宿主负责执行、权限与可恢复状态。

当前主要矛盾是产品目标已经转向自主审计，执行与交付仍分散在先前按阶段、工作流和路径队列扩展出来的体系中。增加解析能力有价值，但不能单独解决消息回执、暂停归因、恢复、验证接线和过时需求继续占用开发队列的问题。

## 对所提供网页 GPT 评价的修正

其关于真实检出效果、误报、成本、证据和复现的目标合理，但有三点需要落实到当前事实。

1. **当前默认分析已采用 Joern。** 已提交的 [主引擎说明](analysis-engine.md) 将默认四阶段固定为 Joern，内置 Go 前端用于兼容与显式自定义工作流。因此，优先自研 Go 类型和数据流分析，需要由主要目标语言、实际漏报样本和引擎能力差距来证明，不能直接作为总重构的第一步。
2. **已有评测，指标还需要纠正。** [运行时对照报告](bench-runtime-report.md) 保存了 80 个合成任务、两个运行时各三次重复、共 480 次真实模型运行的历史结果；验证器当时未启用。它既不等于真实项目漏洞基准，也不能按当前汇总器的 recall/FP 直接判断产品效果。
3. **用户遇到的半完成能力有具体交付断点。** [验证文档](verification.md#known-limits-of-this-slice) 明确 v2 计划和执行为 API-only；[项目停止说明](design/task-state-and-path-stop-20261022.md#范围) 明确 stop-paths 尚不是 #69 的完整项目控制批次。这些问题需要执行主线和验收切片重构，补静态分析无法替代。

## 已确认的重要问题：基准的阳性定义不正确

> 2026-11-17 状态更新：R0 已修复该口径。报告 schema 升至 v2，分别记录
> candidate TP/FN/FP/TN、弃权、执行失败、undecidable、edge 和独立动态验证。
> 下文保留发现当时的问题与复现，作为历史依据；2026-10-20 的 v1 汇总仍不可按
> 新口径重算，因为原始样本未保存。当前口径见 [runtime benchmark](bench-runtime.md)。

[internal/bench/report.go](../internal/bench/report.go) 的 `rates()` 目前把 `candidate` 与 `refuted` 都放入同一个 conclusive 分支：

```go
positive := sample.Label == "vulnerable"
conclusive := sample.Predicted == "candidate" || sample.Predicted == "refuted"
```

后续用 `positive && conclusive` 计算 TP，用 `!positive && conclusive` 计算 FP。因此，在常规漏洞检出含义下：

| 样本 | 模型结论 | 当前汇总器记账 | 应表达的结果 |
|---|---|---|---|
| 已知有漏洞 | refuted | TP | 未检出该漏洞，不能记为 TP |
| 已知安全 | refuted | FP | 正确排除，不能记为 FP |

本轮用已提交源码的独立副本调用现有 `bench.Aggregate`，给出以上两个样本，实际得到 `recall=1`、`false_positive_rate=1`、`success_rate=1`。没有修改项目实现或新增项目测试。

此外，`!positive` 包含 safe、undecidable、edge，三者不应直接共用普通负样本的定义。现有测试覆盖了 safe/inconclusive，未覆盖上述 safe/refuted 记账差异。

这意味着历史报告中约 0.90–0.92 的 recall 和约 0.65–0.71 的 FP 不能按通常的召回率、误报率解释；不能据此断言系统真实误报率就是这些数字。下一步应先确定候选检出、正确排除、弃权/不可判定、执行失败、验证成立的独立口径，并用小型混淆矩阵测试汇总器，再重新汇总原始样本。

## 架构与交付断点

### 多个执行域缺少完整的项目级组合语义

现有组合根同时连接 workflow runner、resident scheduler、review batch、路径 Agent、supervisor 和验证执行器，见 [app.go](../internal/app/app.go)。这些执行域各自有合理职责，多个状态机本身并不是错误；问题在于用户的一次审计横跨这些执行域时，父子关系、暂停原因、消息应用、恢复和最终收束尚未统一。

- #111 已修过旧调度器领取 workflow 路径的问题，表明队列所有权确实需要明确协调。
- #114/#115 已补批次与主运行的 owner/epoch 栅栏，属于应保留的可靠机制。
- stop-paths 目前遍历任务、取消所属工作流、关闭调度、处理路径和暂停运行；它没有替代完整的主 Agent、独立插件、导入及环境生命周期。

建议统一的是作业身份、父子关系、所有者、取消/恢复协议与事件引用；每种执行器仍保留其专业状态。例如验证结论与环境 cleanup 必须继续分开，不能为了统一而把它们压成一个状态字段。

### Agent 工具接口仍让模型承担过多协议工作

[supervisor_project_tools.go](../internal/api/supervisor_project_tools.go) 的项目操作目录只有 operation 和路径 parameters，`project_api.body` 仍是自由 map；大型写响应仍通过 4000 字节窗口返回，非 GET 不允许读取续页。#81/#82 对应的缺契约、缺稳定写入回执问题仍有当前代码依据。

保留通用项目操作作为高级能力，但主要审计动作应提供有类型的领域工具，例如创建调查子任务、发送方向消息、等待结果、申请验证环境、执行已授权探针、提交证据。工具应返回稳定的作业/资源 ID、状态、版本和详情读取位置。模型自主选择工具与调查策略，宿主承担正式执行语义；模型不应靠多轮错误猜测请求包装和字段单位。

### 当前事实缺少唯一入口

- README 仍写只有 Go 前端、部分 supervisor 能力尚为计划；主引擎说明已记录 Joern 接入。
- `bench-runtime.md` 的 Current status 仍写没有真实模型评测、默认保持 llm；后来的报告已记录真实运行并决定切换为 Pi。
- 一些 Issue 的原始验收是完整正式页面，实际切片文档却明确 API-only；这类差异需要回到当前产品计划重新归属。

建议只保留一份短的当前产品能力矩阵，分别列出已可用、受限可用、实验、已弃用。历史设计保留日期和 superseded 指向，避免它们继续充当当前开发指令。

### 自动检查与真实用户闭环之间仍有距离

[CI 配置](../.github/workflows/test.yml) 的 push 只触发 main，另有 pull_request；本次查询没有找到 dev 的 Actions 运行或 PR。当前本地检查通过，说明不能把问题概括为“没有测试”；但它们没有证明主 Agent → 子任务 → 动态验证 → 报告 → 重启恢复这一完整目标可用。

后续每个开发检查点都应在实际使用的分支触发自动检查，并为主线保留小型、真实执行的集成样例。依赖配置、真实执行器和明确 oracle 的测试，与脚本运行时回归分开命名和报告。

## 重构范围建议

| 保留并验证复用 | 优先重构 | 暂缓扩展 |
|---|---|---|
| 不可变输入与产物摘要 | 主 Agent 到子作业的协调与消息回执 | 通用工作流编辑器的新能力 |
| 证据来源、固定版本与历史引用 | 父子作业的取消、恢复、状态收束 | 第二套运行时的功能对齐 |
| 认证、项目归属、审批与宿主执行检查 | 有类型工具与稳定写入回执 | VM 等第二环境后端，除非目标确实需要 |
| PG 持久化、CAS、owner/epoch 与幂等语义 | 环境供应、验证执行和证据收集的正式主线 | 未经校准的置信度模型、CVE 模板扩张 |
| Joern 适配与已有事实查询 | 可读且准确的任务/验证工作台 | 独立对象服务或插件平台的泛化扩展 |

“暂缓”表示不作为新主线的交付前置条件，现有可用能力及历史读取保持兼容；是否正式弃用应由新路线图明确记录。

## 可验收的推进顺序

1. **先确定评测和当前事实。** 修正上述指标口径，冻结可运行基线，选一种主要目标栈和一对有漏洞/已修复样本。固化 expected evidence，避免用模型自评当 oracle。
2. **完成最小自主审计闭环。** 用户给目标，主 Agent 自主调查并委派一个真实子任务；通过宿主批准的能力创建环境，运行可判定的验证，留下证据和报告。静态工具可以失败或部分覆盖，失败应成为调查事实，不能伪装成功或抹去已有源码证据。
3. **把控制与恢复做到这条闭环中。** 运行中追加方向消息并看到应用回执；暂停/停止由执行器确认；硬停后恢复，不重复成功写入、扩大授权或丢失证据；环境清理状态独立可查。
4. **再迁移其他入口。** 让原 workflow、批次、HTTP/MCP 和 UI 逐步调用新执行内核。先保留旧产物和查询适配，再按实际需要迁移历史业务，避免同时重建所有表和所有页面。
5. **用结果决定继续投入。** 在固定样本、模型、工具和资源条件下，与静态工具单独运行、Agent 不用图谱、Agent 使用图谱三种配置比较。扩大语言、运行时或环境后端必须能解释收益。

基准至少分开报告：候选召回/精确率、正确排除、弃权和失败率、可用验证环境覆盖、独立验证成立率、每个真实成立发现的总 token、端到端耗时、重启恢复和取消成功情况。对不可判定或未成功搭建环境的样本单独计数，不能为了提高成功率将其静默删除。

## Issue 与交付方式

原有开放 Issue 是历史需求记录，不应继续自动成为下一步工作队列。新目标确认后，把条目明确归为当前阻塞、当前下一切片、后续提案、被替代或不再实施；被替代/不再实施的可用 not_planned 关闭并链接替代方向，不必等待实现。

当前更接近核心阻塞的包括主子协调/控制、操作契约/回执、输入正确性、执行诊断及单环境验证闭环。置信度排序、报告模板、VM 与独立产物服务不能抢占完整主线的收尾工作。

每个活跃 Issue 应包含一个可运行的用户操作及失败/恢复验收。底层模块阶段完成但尚未接通时，明确维持实验状态；不以新增一组后续 Issue 代替当前承诺的闭环。单次开发集中一个小切片，合并前回到真实默认配置验收，再进入下一个切片。

本轮仅新增评估文档，没有修改上述问题的产品实现，没有创建或关闭新的 GitHub Issue，也没有提交、推送或调整分支。
