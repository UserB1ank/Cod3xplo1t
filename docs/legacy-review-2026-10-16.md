## 原始问题与解决方案（复核基线）

### LR-01：将审计额度检查和领取放入同一原子操作

代码位置：[Service.Claim](../internal/path/service.go)、
[AgentCoordinator.ClaimSpecificPath](../internal/graph/agentcoordinator.go)、
[Memory.ClaimPath](../internal/storage/memory_audit.go)、
[SQL.ClaimPath](../internal/storage/sql_audit.go)。

两个入口都先读取活跃路径数，再调用 `Store.ClaimPath`。后者保证同一路径不被重复
领取，却没有在原子操作内检查整个审计的活跃上限。两个请求可以同时看到空闲额度，
随后领取不同路径。调度器也直接调用该存储方法，单实例的并发预算无法提供跨实例
的审计额度保证。

建议在存储层提供统一的领取操作：检查审计状态、核验审计额度、校验路径状态与
租约、修改路径、追加事件，一次提交。Memory 在同一把锁内完成；SQLite 在同一
写事务内串行化审计额度的分配。所有入口均经过该操作，包括常驻调度器。已有持有者
续租不重复消耗额度。单独增加进程内 mutex 不能覆盖多个服务进程。

验收条件：上限为 1 时，多 worker 竞争不同路径也只能产生一个活跃路径；释放、
过期回收、失败与完成后额度均可恢复；同持有者续租正常；事件与领取结果一致。
同时覆盖队列领取、指定路径领取、调度器以及两个 SQLite 连接的竞争。

### LR-02：统一快照登记，提供显式的历史导入

代码位置：[buildSCGChain](../cmd/cli/scg.go)、
[API 快照处理](../internal/api/server.go)、[快照表](../migrations/0001_init.sql)。

CLI 构建链写入磁盘和图表，却不调用 `PutProject`、`PutSnapshot`、`PutManifest`。
API 通过存储查询，因此同一个工作区出现两种快照视图。

建议抽取共享的快照登记服务：基于仓库稳定身份生成项目标识，CLI 的 SCG/ASG/audit
构建链与 API 都调用它，按项目、快照、manifest、派生图的依赖顺序登记。
`snapshot`/`manifest` 当前明确支持无数据库使用，可以保留这一模式，但应提供
`snapshots register/import --project ... --db ...`，并清楚显示是否已经登记。
按仓库建立隐式项目比让所有本地仓库共享一个 `local` 项目更符合现有模型。

历史修复由显式导入执行：核验 snapshot 身份、现有 manifest 与图的关联，幂等地补齐
记录，冲突时报告具体原因。避免在 `Store.GetSnapshot` 内静默创造记录。

验收条件：CLI 构建后，使用相同工作区和数据库的 API 能列举、查询快照和 manifest；
重复构建不增加项目或快照；历史导入可重跑；规则或配置不一致时保留冲突语义。

### LR-03：CLI 和 API 使用同一删除服务

代码位置：[runSnapshots](../cmd/cli/main.go)、
[存储删除实现](../internal/storage/sql.go)、[内存删除实现](../internal/storage/memory.go)。

`snapshots remove` 固定打开 `DBPath: "memory"`，只调用 `Manager.Remove`。
数据库中的图、ASG、审计、运行、证据和 findings 因而没有经过已有的级联删除逻辑。
本次直接验证了图数据残留；其他派生表存在同样的绕过路径。

建议增加 `--db`，默认使用工作区数据库，调用与 API 共享的删除服务。对未登记的
纯磁盘快照提供明确的处理分支；自定义数据库的工作区应显式选择正确数据库。
删除前应协调活跃任务，防止 worker 在删除过程中继续写回派生记录。

验收条件：CLI 删除已登记快照后，磁盘和所有派生查询均不再返回数据；纯磁盘快照
仍能删除；自定义 `--db` 可用；活跃任务删除的拒绝或停止策略有明确结果。

### LR-04：为跨数据库与文件系统的删除增加恢复状态

代码位置：[handleDeleteSnapshot](../internal/api/server.go)、
[Manager.Remove](../internal/repository/manager.go)、`contracts.md` §3。

当前先提交数据库删除，再清理磁盘。磁盘失败后没有持久化的待清理记录，下一次请求
在数据库的 `ErrNotFound` 处返回，无法到达磁盘清理步骤。

建议把删除建模为可恢复操作：先持久化 `DELETING` 状态或删除任务，阻止新的构建与
领取，处理活跃 worker，幂等清理目录，再完成派生记录清理。任务直到两侧清理完成
才结束，重试与服务重启均能继续。只交换两步的先后顺序，会把故障窗口转移到数据库
清理失败，仍不能提供完整恢复。

验收条件：在目录清理失败、数据库提交失败、进程中断三个位置注入故障后，重试均能
收敛；清理完成后重复 DELETE 的语义稳定；清理中的快照不能被当作正常任务使用。

### LR-05：将项目修改改为存储层 CAS

代码位置：[handlePatchProject](../internal/api/server.go)、
[SQL.PutProject](../internal/storage/sql.go)、[Memory.PutProject](../internal/storage/memory.go)。

处理器先读取项目并检查 ETag，随后解析请求体，再用无条件 upsert 写回。
两个请求都能通过旧 ETag 检查，之后依次覆盖项目名。现有
`TestProjectOptimisticConcurrency` 验证的是顺序请求，未覆盖这一交错。

建议引入显式项目版本号和条件更新接口：SQL 使用
`UPDATE ... WHERE id = ? AND version = ?`，Memory 在锁内比较并修改版本。
未更新到记录时映射为 HTTP 412。更新接口直接返回本次提交的项目，避免再次读取时
混入另一请求的修改，并据此生成 ETag。

验收条件：两个相同版本的并发 PATCH 恰好一个成功，另一个返回 412；响应正文和
ETag 对应同一次提交；现有缺少 If-Match、过期版本与非法请求用例继续通过。

## 建议实施顺序

1. **先落实原子约束**：LR-01；LR-05 可独立处理。新增测试应控制并发交错，验证
   审计上限和条件更新的业务结果，不能仅依赖 race detector。
2. **统一快照生命周期**：LR-02 → 共享删除服务 → LR-03/LR-04；提供显式导入与
   删除恢复，覆盖历史工作区和自定义数据库。
3. **整理工程入口与问题清单**：纠正过期条目，补缺失文档和发布目标，确定模块地址，
   修正格式检查范围，安排 lint 与发布工作流。
4. **改善证据质量和可用性**：类型索引、常量传播、历史评分留存、评分基准和 MCP
   只读查询。分析结果变化必须同步更新对应引擎/规则版本与身份，保留旧证据来源。
5. **按产品需求扩展**：数据流、增量、多语言、验证队列、WebUI 与分布式协调分别
   建立验收指标，保留现有明确的证据与部署边界。
